#+title: Covercrypt Road-Map

* Planned [3/5]

** DONE Make hierarchical broadcasts bottom (⊥) attributes         :breaking:
<2026-10-27 Tue>

Currently, hierarchical dimensions (e.g. ~H~) include a broadcast element
(e.g. ~H::*~) that is derived for all user secret keys and used to generate
encapsulations for access policy that don't mention this dimension (e.g. ~D::A~
for some dimension ~D~ different from ~H~ and attribute ~A~ in ~D~). However,
both ~H::*~ and its lowest element ~H::⊥~ are redundant.

Indeed a user secret key derived for an access policy ~D::A~ would be granted
keys for all combinations of ~D::A~ with an attribute in ~H~, which includes
both ~D::A && H::⊥~ and ~D::A && H::*~, while a user secret key derived for an
access policy ~D::A && H::B~ (where ~B~ is some attribute in ~H~ that is not
~H::*~) would also be granted the broadcast key in ~H~, /i.e./ ~D::A &&
H::*~. In other word, there is no user secret key holding a key for some
combination of attributes including ~H::⊥~ but not for the same combination of
attributes including ~H::*~ instead.

The size of the universe is therefore unnecessarily increased.

This MR proposes to consider the broadcast attributes of hierarchical dimensions
to be their bottom elements instead. As a consequence, when extending an access
policy with attribute combinations from its complementary space, hierarchical
dimensions are ignored.

*BREAKING*: This is a breaking change since it changes the decapsulation power
of all user secret keys which access policy does not mention a hierarchical
dimension.

An alternative implementation could have removed the broadcast element. The
difference is that it would allow naming the bottom element of hierarchical
dimensions. However, it would also allow changing its name for example by adding
an attribute that is lower than the current bottom attribute, breaking the
meaning of previous encapsulations for which this attribute was implicitly
derived. Additionally, its implementation is slightly more involving.

** DONE Access-policy parser generation                          :compatible:
DEADLINE: <2026-10-23 Fri>

For now, parsing access policies is performed by hand parser. We propose to use
a parsing library to generate parsers from the abstract grammar instead. This
change should bring the following overall improvements:
- simplify and improve the overall robustness of access-policy parsing;
- simplify auditing the compliance with the coming Covercrypt standard;
- allow to add /new features/ to the language such as:
  - [X] specifying a version number for each qualified attribute
  - [X] specifying a version tag for each qualified attribute

** DONE Allow generating subspace MPKs                             :breaking:
DEADLINE: <2026-10-23 Fri>

The proposed implementation makes the MSK method ~mpk~ private outside of the CC
crate and exposes instead a procedure ~gen_mpk : msk -> policy option -> (mpk,
error) result~ in the CC interface (~api.rs~).

The behavior of ~gen_mpk msk None~ is identical to the old ~msk.mpk()~ while
~gen_mpk msk Some(ap)~ returns an MPK that limits the encapsulation power to a
subset of the ~ap~ policy.

** TODO Strong authentication upon update                          :breaking:
DEADLINE: <2026-11-06 Fri>

*** Problematic

As of now, the USK update procedure has the following signature:
#+begin_src ocaml
  val update: msk -> usk sealed -> usk sealed
#+end_src

It therefore relies on an external system for authenticating and filtering out
users that have been expelled from the system. This is sub-optimal since
authentication may not be linked user keys, in which case an authorized user
could request an update of the key of an unauthorized user.

*** Proposed solution

Guaranteeing a user secret key cannot be updated after being excluded from the
system can be done in two ways: using a block-list, or using an allow-list.
Using an allow-list requires storing an information for each user in the system,
which is O(|U|) space. Using a block-list requires storing an information for
each expelled user, which is O(#ban). In other words, one solution is function
of the working set while the other is function of the history of the system.
The choice of the optimal solution may depend on the use-case, but in the worst
case, the space usage of the block-list solution is /unbounded/ while it is safe
to assume that the number of users present in the system to be /bounded/. Hence,
we propose to adopt the allow-list approach.

Concretely, we propose to store in the MSK the user ID (~uid = H(α,β)~) of each
active user (which requires ~16·|U|~ space). Update request for keys which user
ID is unknown are rejected. An additional ~ban : msk -> uid -> msk~ procedure is
added to the Covercrypt API.

*Note*: we might want to allow external user IDs to be used in which case the
master secret keys stores the following map: ~uid -> H(α,β)~ (which requires
~(16 + 16)·|U|~ space).

*Note*: we might want to allow the MSK to re-generate any user secret key, in
which case it needs to store the following map: ~uid -> (α, β, apᵤ)~.
Alternatively, it can store the map ~uid -> (seedᵤ, apᵤ)~ where ~seedᵤ~ is the
random seed used as source of random for generating the Covercrypt identity ~(α,
β)~ of the user (which requires ~(16 + 16)·|U| + ∑ sizeof(apᵤ)~ space).
